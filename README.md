# 활력 파트너스

Next.js App Router + Supabase Auth/Postgres + Vercel용 회원·구매·배송·보너스 관리 앱입니다.

## 관리자 사이트 / 회원 웹앱 분리

| 서비스 | 경로 | 구성 |
|---|---|---|
| 관리자 운영 사이트 | `/admin` | PC 중심 대시보드, 회원 관리, 기간별 매출, 수동 충전, 배송, 조직도, 정산 |
| 관리자 로그인 | `/admin/login` | 관리자 전용 로그인, 회원가입 없음 |
| 회원 웹앱 | `/app` | 모바일 중심 홈, 내 PV·한도, 보너스, 구매·배송, 내 정보, 하단 메뉴 |
| 회원 로그인/가입 | `/login` | 일반 회원 로그인과 주소를 포함한 가입 |

루트 `/`는 회원 웹앱으로 이동합니다. 두 서비스는 별도 페이지와 화면 컴포넌트를 사용하며 모드 전환 UI를 공유하지 않습니다. 데이터베이스와 정산 규칙만 공유합니다. 관리자 사이트는 서버에서 역할을 확인한 뒤 전체 정보를 읽습니다. 회원 앱은 관리자 계정으로 열어도 본인 ID 조건으로만 조회하며 다른 회원 목록과 관리자 감사 기록을 내려보내지 않습니다. 웹앱 manifest 범위는 `/app`으로 한정하고 개인정보의 오프라인 캐시는 만들지 않습니다.

샘플 관리자 사이트는 `김민준`, 회원 앱은 `이서연`의 화면입니다. 같은 브라우저의 관리자 사이트에서 이서연을 충전하거나 배송 상태를 바꾼 뒤 회원 앱을 열거나 새로고침하면 해당 변경을 확인할 수 있습니다.

## 실행

Node.js 22 이상을 권장합니다.

```sh
npm ci
npm run dev
```

`http://127.0.0.1:3000/app` 또는 `http://127.0.0.1:3000/admin`을 엽니다. Supabase 환경변수가 없으면 개발 환경에서 샘플 데이터로 실행합니다. 샘플 변경은 해당 브라우저에만 저장되며 관리자 사이트의 초기화 버튼으로 복구합니다. 실제 서버 데이터와 연결되지 않습니다. 운영 환경에서는 `ENABLE_DEMO=true`를 명시하지 않는 한 샘플 화면을 제공하지 않습니다.

## 실제 서비스 연결

1. 이번 앱에 사용할 Supabase 프로젝트를 정합니다. 기존 다른 앱의 프로젝트에는 이 스키마를 적용하지 마세요. `members`, `purchases` 테이블과 Auth 가입 트리거를 설치합니다.
2. 신규 DB에는 `supabase/migrations/`의 모든 SQL을 파일명 순으로 적용합니다. 이미 설치된 운영 DB에는 아직 적용하지 않은 새 마이그레이션만 실행합니다.
3. `.env.example`을 `.env.local`로 복사하고 Project URL과 publishable key를 넣습니다. 서비스 비밀키는 사용하지 않습니다.
4. Supabase Auth에서 이메일 가입, 이메일 확인, 사이트 URL 및 Redirect URL을 설정합니다. 가입 시 이메일 인증을 마친 뒤 로그인합니다. 기본 이메일 템플릿의 확인 링크를 사용할 수 있습니다.
5. `/login`의 회원가입에서 관리자 본인의 계정을 먼저 만들고 이메일 인증을 완료합니다.
6. SQL Editor에서 아래 이메일을 실제 관리자 이메일로 바꿔 최초 관리자만 지정합니다. 이 역할은 회원이 수정할 수 없는 데이터베이스 열로 확인합니다.

```sql
update public.members
set role = 'admin'
where email = '관리자 이메일';
```

7. Supabase Integrations에서 Cron을 활성화하고 `supabase/enable-scheduler.sql`을 SQL Editor에서 실행합니다. 매일 한국 시간 00:01에 전일까지의 미정산 직급 보너스를 처리합니다. 기본 UTC 스케줄을 기준으로 작성했습니다. 운영 설정 화면에서도 마감일을 선택해 중복 없이 실행할 수 있습니다.
8. Vercel에 이 폴더를 저장한 Git 저장소를 연결하고 Framework를 Next.js로 선택합니다. 환경변수 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 등록합니다. 운영에서는 `ENABLE_DEMO`를 삭제하거나 `false`로 설정합니다. 별도 상시 서버나 파일 저장소는 필요하지 않습니다.
9. 배포 도메인을 Supabase Auth의 Site URL/Redirect URL에 반영합니다.

## 사용 흐름

- 회원: 이메일·비밀번호·이름·전화번호·우편번호·주소·상세주소 입력 → 이메일 확인 → 로그인 → 본인 구매/배송/보너스 확인.
- 관리자: 회원 관리에서 추천인, 후원 상위 회원과 좌·우 위치, 소속 센터를 지정 → 입금을 실제로 확인 → PV 충전 → 회원이 PV로 상품 구매 → 미배송 주문 생성 → 배송완료 처리.
- 수동 충전은 입금액에 맞는 PV만 추가합니다. 최초 충전은 37만원/30만 PV, 추가 충전은 27만원/20만 PV입니다. 충전 단계에서 주문·한도·보너스를 생성하지 않습니다.
- 센터: 운영 설정에서 센터명과 센터 등급 회원(보너스 수령인)을 등록합니다. 해당 회원은 센터 등급으로 표시됩니다. 회원 정보 수정에서 소속 센터를 배정합니다. 센터 등급은 관리자 권한과 별개입니다.
- 관리자는 구매 여부와 관계없이 추천·후원인 및 좌·우 배치를 수정할 수 있습니다. 후원인을 변경하면 해당 회원의 하위 조직도 함께 이동합니다. 자기 지정·순환·중복 자리는 차단하며 이전/변경 후 관계를 감사 기록에 남깁니다. 이전 보너스 기록은 유지합니다.
- 상품 배송지는 구매 승인 시점의 주소를 복사하여 보존합니다. 이후 회원 주소 수정으로 이미 생성된 주문의 주소가 바뀌지 않습니다.

## 확정된 정산 규칙

| 처리 | 입금/결제 | PV 변동 | 한도 추가 |
|---|---:|---:|---:|
| 최초 충전 | 370,000원 입금 | +300,000 PV | 없음 |
| 추가 충전 | 270,000원 입금 | +200,000 PV | 없음 |
| 상품 구매 | 300,000 PV 결제 | -300,000 PV | 1,500,000원 |

상품을 구매할 때만 한도와 보너스가 발생합니다. PV 상품의 최초/재구매는 상품 주문 이력으로 판별합니다. 충전 이력과 독립적입니다.

- 모든 보너스: 남은 한도 내에서만 지급. 초과액은 즉시 소멸. 정지 중 발생분은 적립/이월하지 않으며 재구매 후 새로 발생한 보너스부터 지급합니다.
- 추천: 최초 구매 PV의 1대 30%, 2대 10%. 추천 관계를 따릅니다.
- 삼각 1: 본인과 직속 좌·우의 새 PV 상품 구매가 각 1회 모일 때마다 90,000원.
- 삼각 2: 직속 후원 회원의 삼각 매칭마다 상위 회원에게 90,000원(좌·우 각각 발생 가능).
- 삼각 3: 후원 2대 회원의 삼각 매칭마다 상위 회원에게 60,000원(최대 4개 위치에서 발생 가능).
- 최초/재구매 모두 계산하며 매칭마다 본인·좌·우 구매 1회씩 FIFO로 소비합니다. 미매칭 실적은 이월하지만, 완료된 매칭의 한도 초과분은 소멸하며 재구매 후 복구되지 않습니다.
- 실적의 좌·우 소속은 구매 시점 후원 배치로 고정됩니다. 배치 변경으로 이미 발생한 실적을 이동하거나 재사용하지 않습니다. 삼각2·3 수령인은 매칭 완료 시점의 상위 후원자입니다.
- 전환 전 완료 가능한 조합은 기존 정산 기준으로 소비 처리하여 과거 보너스를 재생하지 않습니다. 기존 보너스 원장은 유지하고 남은 미매칭 실적만 이월합니다.
- 재구매 후원 롤업: 후원 배치 상위 최대 13대에 각 10,000원(고정). 존재하지 않는 세대분을 다른 회원에게 넘기지 않습니다.
- 센터: 관리자가 소속시킨 회원의 구매 PV 5%. 30만 PV 상품은 최초·재구매 모두 15,000원. 후원 조직과 독립적으로 적용하며, 한 구매에 소속 센터 하나에 지급합니다.
- 팀장: 활성 구매 회원 5명 직접 추천. 본부장: 팀장 3명 직접 추천. 센터 등급은 표시 시 우선하며, 추천 실적으로 충족한 공동 보너스 자격은 별도로 계산합니다.
- 일일 직급 공동 보너스: 재구매 PV의 20%를 팀장·본부장에게, 10%를 본부장에게 균등 배분합니다. 원 미만 나머지는 회원 UUID 순으로 1원씩 배분합니다. 자격자가 없는 풀은 다른 회원에게 재분배하지 않습니다.
- 직급은 마감 시점의 자격으로 계산합니다. 예약 실행이 늦어졌을 때 새 상품 구매나 회원 변경 전에 지난날 정산을 먼저 처리하여 재구매가 과거 소멸분을 되살리지 않도록 했습니다.

보너스 원장은 **발생액·지급액·소멸액·사유**를 기록합니다. 여기서 지급은 내부 보너스 기록 반영을 뜻하며, 은행 송금·출금 신청·세금 처리는 구현 범위에 포함하지 않습니다.

## 접근 제어와 데이터 무결성

- 회원은 본인 개인정보·구매·보너스와 본인 산하의 조직도(이름·회원코드·배치만)를 조회합니다. 관리자는 전체를 조회합니다. 센터 등급만으로 타인의 개인정보 접근 권한이 생기지 않습니다.
- 모든 공개 테이블은 RLS를 활성화하고 직접 INSERT/UPDATE/DELETE 권한을 제거했습니다. 관리 변경은 관리자 여부를 검사하는 RPC로만 수행하고, PV 구매는 로그인한 활성 회원 본인만 실행할 수 있는 RPC로 처리합니다.
- 권한은 `user_metadata`가 아니라 데이터베이스의 역할과 상태를 조회합니다. 공개 스키마의 RPC는 SECURITY INVOKER이며, 권한이 필요한 내부 함수는 비공개 스키마에 두고 EXECUTE 권한을 명시합니다.
- 상품 주문 생성, PV 차감, 한도 추가, 실시간 보너스는 하나의 DB 트랜잭션입니다. 입금 충전은 별도 pv_topups 원장에 기록합니다. 요청 UUID로 재시도 중복을 방지합니다. 금융 변경은 트랜잭션 잠금으로 직렬화합니다.
- 순환 추천/후원 관계, 이미 찬 좌·우 자리, 관리자 자신의 이용 정지를 차단합니다.
- 현재 UI는 서버에서 전체 허용 데이터를 500건씩 읽어 받은 뒤 화면별 10건씩 표시합니다. 초기 운영용 구조이며 대규모 데이터에서는 서버 집계와 검색별 페이지 조회로 확장하는 것이 좋습니다.

## 검증

```sh
npm test
npm run build
npx playwright test
```

DB 테스트는 PGlite의 실제 PostgreSQL 엔진에 Supabase Auth 인터페이스를 모사한 최소 스키마를 만들고 설치 SQL을 실행합니다. RLS, 일반 회원/익명 거부, 구매 중복 방지, 주소 보존, 한도/소멸, 삼각 1·2·3, 센터 PV 5%, 직급 마감 재실행을 확인합니다. 클라우드 Supabase Auth 이메일 전달 및 예약 작업은 대상 프로젝트 연결 후 별도 확인이 필요합니다.

브라우저 테스트는 개발 서버가 실행 중이어야 하며 로컬 Microsoft Edge를 사용합니다. 충전·배송완료·회원 수정·조직도·새로고침 유지·모바일 레이아웃·회원가입 주소 필드를 확인합니다.

## 회원 상품 구매와 조직도

- /app/products: 활력단 15개를 300,000 PV에 구매합니다. 주문 확인 후 보유 PV 차감, 배송지 보존, 미배송 주문 생성, 한도 1,500,000원 추가와 보너스 처리를 원자적으로 실행합니다. PV 결제에 추가 PV 충전은 없습니다.
- PV 구매의 보너스 기준은 구매액 300,000 PV입니다. 재구매 후원 13대 각 10,000원(고정), 소속 센터 15,000원, 일일 공동 보너스에도 해당 PV를 포함합니다. 현금은 PV 충전만 처리하며 보너스 계산 대상이 아닙니다. 삼각 보너스는 본인·좌·우 구매 실적의 반복 매칭으로 지급합니다.
- 관리자는 기존 배송 관리/회원관리에서 PV 주문도 배송 처리합니다. 입금액은 충전 원장에서 집계하고, 상품 주문은 PV 결제로 표시합니다.
- /app/organization: 추천/후원 전환, 좌·우 배치, 하위 회원 선택, 이전 단계/본인 복귀. 각 단계는 최대 50명씩 조회하며 다른 조직과 연락처·주소·잔액은 노출하지 않습니다.
- 기존 DB에는 supabase/migrations/20260910103130_member_shop_and_organization.sql 및 20260910104005_fixed_rollup_bonus.sql, 20260910105529_separate_pv_topups.sql을 순서대로 추가 적용해야 합니다. 신규 DB에는 모든 마이그레이션을 파일명 순으로 적용합니다.

## 보관형 종합 테스트

`npx tsx scripts/validate-bonus-scenario.ts`로 18대 후원 조직, 40명, 모든 직급/보너스와 한도 경계 검증을 실행합니다. 실행별 고유 디렉터리 `validation-runs/`에 실제 PostgreSQL 호환 PGlite DB, 전체 원장 CSV, JSON, HTML 보고서를 보존합니다. 기존 실행 기록은 삭제하지 않습니다. DB 디렉터리는 로컬에 보관하며 Git에는 보고서·CSV·실행 스크립트를 저장합니다. Auth는 테스트용 인터페이스이며 운영 Supabase와 분리되어 있습니다.

## 회원 계좌 정보

신규 가입 시 국내은행·계좌번호·예금주는 선택 입력입니다. 세 항목을 모두 비우면 계좌 없이 가입되며, 계좌를 등록할 때는 세 항목을 함께 입력합니다. 계좌번호는 하이픈/공백을 제거한 문자열로 저장하여 앞자리 0을 보존합니다. 기존 회원은 미등록 상태를 유지하며 /app/profile에서 등록·수정할 수 있습니다. 관리자는 회원관리의 정보 수정에서 계좌를 확인·수정합니다. 본인과 관리자만 조회 가능하며 조직도에는 계좌를 노출하지 않습니다. 변경 기록에는 계좌번호를 기록하지 않습니다. 계좌 정보 등록 기능이며 은행 실명 조회나 송금 기능은 포함하지 않습니다. 기존 설치에는 20260910115445_member_bank_details.sql과 20260910120151_optional_signup_bank.sql을 순서대로 적용합니다.

추천·후원 수정 허용은 20260910121800_editable_member_relationships.sql에 반영되어 있습니다.


## 회원 아이디 로그인

가입 시 영문으로 시작하는 4~20자의 영문·숫자·밑줄 아이디를 입력합니다. 아이디는 소문자로 정규화하며 DB 고유 제약으로 중복 가입을 막습니다. 이메일은 가입 인증용으로 유지합니다.

기존 계정에는 소문자 회원코드를 아이디로 지정하며 기존 이메일 로그인도 유지합니다. 회원 내 정보와 관리자 회원 상세에서 아이디를 확인할 수 있습니다. 아이디→인증 이메일 조회는 서버의 SUPABASE_SERVICE_ROLE_KEY 전용 RPC로 처리하며 익명/회원에게 이메일 조회 권한을 부여하지 않습니다. 비밀번호 검증과 세션은 Supabase Auth를 사용합니다.
